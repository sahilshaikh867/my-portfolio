Overview

What this project is about

This project simulates a real production environment where a user accesses a web application over HTTPS, traffic is routed via a load balancer, application servers are auto scaled, and the database layer is isolated inside private subnets.

The goal was to design from scratch: networking, security, compute, storage and observability, while keeping the architecture simple enough to rebuild quickly during practice.

Single VPC with public & private subnets Internet Gateway & NAT Gateway Application Load Balancer + Auto Scaling Group RDS MySQL in private subnets S3 for static assets & backups CloudWatch metrics & alerts
Architecture & Workflow

How the infrastructure works end‑to‑end

High‑level flow:

A user types the application URL, Route 53 resolves the DNS to the Application Load Balancer, the ALB terminates HTTPS, forwards the request to EC2 instances in an Auto Scaling Group in private subnets, and these instances talk to an RDS MySQL database over internal security groups. Static assets are served via S3/CloudFront, and all activity is monitored using CloudWatch.

Step‑by‑step deployment workflow
1. VPC & Subnets Created a VPC (10.0.0.0/16), two public and two private subnets across different AZs for high availability.
2. Routing & Internet Attached an Internet Gateway to the VPC, added route tables so only public subnets have direct internet access. Private subnets use a NAT Gateway.
3. Security Groups One SG for ALB (80/443 from internet), one for EC2 (only from ALB SG), and one for RDS (only from EC2 SG). No direct DB access from public internet.
4. EC2 + Auto Scaling Created a Launch Template with the app AMI & user data, configured an Auto Scaling Group in private subnets behind the ALB with CPU‑based scaling.
5. Load Balancer & HTTPS Application Load Balancer in public subnets, integrated with ACM SSL certificate to terminate HTTPS and forward traffic to EC2 targets.
6. RDS & Backups Provisioned RDS MySQL in private subnets with Multi‑AZ, automated backups and proper parameter groups for connection limits.
7. S3, CloudFront & Logs Used S3 for static assets and backup storage, enabled access logs for ALB and S3, and set up CloudWatch dashboards and alarms.
Phase 1 – Design (Paper / Draw.io) Sketched the architecture: VPC layout, subnets, traffic flow and security boundaries.
Phase 2 – Manual build in AWS Console Created and tested each component step‑by‑step using the AWS Management Console.
Phase 3 – Automation preparation Documented all resources and parameters so the same stack can later be automated using IaC (Terraform/CloudFormation).
Learnings

What this project taught me

Key technical takeaways
  • How to separate public and private resources using subnets, route tables and security groups.
  • Designing stateless application servers with Auto Scaling behind an Application Load Balancer.
  • Configuring RDS in private subnets with least‑privilege access from the app layer only.
  • Using CloudWatch metrics and alarms to understand CPU usage, latency and error rates.
What I would improve next
  • Automate the full stack using Infrastructure as Code (Terraform or CloudFormation).
  • Integrate a CI/CD pipeline (GitHub Actions / CodePipeline) to deploy app changes safely.
  • Add WAF (Web Application Firewall) and deeper logging with centralized log aggregation.
